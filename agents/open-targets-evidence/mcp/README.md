# Open Targets MCP connection and testing

This guide describes the existing provider-maintained remote MCP connection and documented Studio/Foundry test paths. It is documentation only: the catalog package does not provision the service, model, credentials or runtime access. Manual Studio setup is distinct from deployment of the catalog YAML.

## MCP tools

- `search_entities`: find entity candidates and their identifiers and types.
- `query_open_targets_graphql`: run a single GraphQL query, including focused schema introspection.
- `batch_query_open_targets_graphql`: run the same query for a bounded list of variable sets.
- `get_open_targets_graphql_schema`: inspect schema by relevant category.
- `get_type_dependencies`: inspect a type and its recursively reachable dependencies.

These are the five tools documented by the provider and observed in the earlier hosted-server tool list. The earlier two-tool allowlist was a deliberate local restriction, not a provider limitation. Category or dependency outputs may be large; the agent can use focused introspection instead. Batch query executions are counted individually, separately from MCP tool calls.

The agent's requested sample, query and batch budgets are prompt instructions, not enforced limits on MCP inputs or remote execution. The GraphQL tools can accept larger queries and batches. If hard limits are required, use a separately verified runtime or service-side limiter; the tool allowlist and requested per-call approval do not themselves impose size ceilings.

## Prerequisites

- An authorized Discovery Studio and Foundry environment for the intended integration test, with a compatible model deployment and access to the Open Targets MCP endpoint. A direct Foundry technical test is a separate path and its accepted configuration format must be verified there.
- Permission to use the model and to connect the external service. Respect the provider's [licence](https://platform-docs.opentargets.org/licence), [terms of use](https://platform-docs.opentargets.org/licence/terms-of-use), attribution guidance, and applicable original-source rights.
- For catalog submission, a publisher name, contact email, and reachable support URL are required. They identify the team responsible for publishing and supporting this agent, not necessarily the provider of its data or MCP server. The contact must have a valid address and usable domain; the support URL must be a reachable public HTTPS HTML page. The current Microsoft first-party publisher block is provisional and must be confirmed by the responsible owner before submission; it does not establish catalog acceptance. These catalog metadata requirements are not asserted as prerequisites for a separate direct Foundry technical test.
- Enterprise prerequisites, network policy, access, licensing, model deployment, and authentication must be confirmed by the deploying team. Local Preview results do not establish enterprise readiness.

## Configuration

`agent.yaml` and `metadata.yaml` are draft Discovery catalog/AgentSchema artifacts, not demonstrated universal Foundry SDK or REST request bodies. Use the actual target interface's documented format rather than assuming it imports these files directly. The separate Preview `.agent.md` definitions and their gateway/file-reader instructions are not part of this Foundry definition.

For a Discovery catalog contribution, the [authoring guide](https://github.com/microsoft/discovery/blob/main/docs/authoring-guides/agent-authoring-guide.md#3-folder-layout) requires [`agent.yaml`](../agent.yaml), [`metadata.yaml`](../metadata.yaml) and the [main README](../README.md). This package also includes this MCP guide. The provisional publisher details need owner confirmation before submission. Historical evidence and test records are retained separately in the local project and are not runtime configuration. Exclude the separate Preview `.github/agents/*.agent.md` definitions from the Foundry definition. A `tools/` directory is optional for custom containerized tools and is not needed for this provider-hosted MCP.

`{{CHAT-MODEL}}` is the model deployment supplied by the target runtime, not a credential. The draft declares a Foundry-native `mcp` entry in top-level `tools`, as allowed by the [authoring guide](https://github.com/microsoft/discovery/blob/a8899c85aee5d8800f5a2a3048dbb20ac6fd2229/docs/authoring-guides/agent-authoring-guide.md#5-agentyaml) and illustrated by newer catalog examples, including [Synthesize Bio](https://github.com/microsoft/discovery/blob/88a2a1cd1664b7d609659dc86c65f7f632686715/agents/synthesize-bio/agent.yaml). `associated_tools: []` means no custom catalog `tools/` subfolders are packaged; it does not itself register or grant the external server.

The [AgentSchema MCP specification](https://github.com/microsoft/AgentSchema/blob/b7833d1ff6888d655643de2f11355e791133b939/schemas/v1.0/McpTool.yaml) describes `connection`, `serverName`, `approvalMode`, and optional `allowedTools`; its [anonymous connection](https://github.com/microsoft/AgentSchema/blob/b7833d1ff6888d655643de2f11355e791133b939/schemas/v1.0/AnonymousConnection.yaml) supports an endpoint and its [always-approval mode](https://github.com/microsoft/AgentSchema/blob/b7833d1ff6888d655643de2f11355e791133b939/schemas/v1.0/McpServerToolAlwaysRequireApprovalMode.yaml) uses `kind: always`. The catalog examples use the same MCP-level fields, but use different connection and authentication settings. The Open Targets anonymous declaration is a **draft for Studio/Foundry testing**: its acceptance, mapping to Foundry, endpoint reachability, tool restriction and approval enforcement have not been verified there. The declaration does not itself provision the endpoint or model.

See [Foundry MCP guidance](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol) and the catalog's [Wiley connection example](https://github.com/microsoft/discovery/blob/a8899c85aee5d8800f5a2a3048dbb20ac6fd2229/agents/wiley-nexus/mcp/README.md) for separate configuration. Wiley's API key and auto-approval instructions are specific to its example and are not established requirements for this Open Targets agent. The intended policy is user approval, not automatic approval; the deploying team must verify approval requests and handling in its actual runtime. These sources are guidance, not a successful deployment test of this package. Never put keys or tokens in these files.

For an authorized Studio/Foundry test, the team needs Discovery Studio and Foundry project access, an existing compatible model deployment for `{{CHAT-MODEL}}`, permission and network access to the hosted endpoint, and a way to review and answer MCP approval requests. Before catalog submission, the responsible publisher's real name, contact and support URL and an IT-approved schema-validation path are separately required. Verify the effective endpoint, anonymous connection, exposed tool scope and approval behavior, then make a bounded read-only call. If anonymous connection or approval is unsupported, stop and report the actual error rather than disabling approval or supplying invented credentials.

Discovery Preview gateway and task-agent setup is supplementary historical evidence, not Foundry configuration.

## Studio and Foundry test paths

The [Discovery agent creation guide](https://learn.microsoft.com/en-us/azure/microsoft-discovery/how-to-agent-creation) documents a private project-scoped **form-based** path without requiring a catalog contribution:

1. In [Discovery Studio](https://studio.discovery.microsoft.com/), select **Projects** and open the intended existing project. Confirm the tenant, workspace, project, permissions and workspace-level model deployment with the environment owner.
2. Select **Discovery > AI Capabilities > Agents > New agent > Create new agent**. Enter the name, description and instructions from `agent.yaml`, select an existing workspace model, and save. Each save creates an immutable version. The guide documents selection of available tools but does not establish how this particular external MCP, anonymous connection, allowlist and per-call approval map into that form.
3. The catalog's [Wiley example](https://github.com/microsoft/discovery/blob/main/agents/wiley-nexus/mcp/README.md) documents a saved Studio agent's **Open in Foundry** action, followed by Foundry **Tools > Tools > Connect a tool > Custom > Model Context Protocol > Create**, entering a remote endpoint, connecting the project-level tool and using **Use in an agent** to attach it. It describes a Foundry project backing the Discovery workspace; confirm which project this tenant actually uses and whether this UI path is available. If the intended connection is already present there, inspect it rather than creating a duplicate. Wiley's API key, empty allowlist and auto-approval are specific to that example and must not be copied.
4. For this draft, the intended endpoint is `https://mcp.platform.opentargets.org/mcp`; the [Foundry MCP guide](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol) describes public endpoints and user approval, and a separate [SQL MCP quickstart](https://learn.microsoft.com/en-us/azure/data-api-builder/mcp/quickstart-azure-ai-foundry) shows an **Unauthenticated** option in that example's Foundry UI. The server responded without credentials in a limited local test, and a later manually configured Foundry search succeeded as observed by the user. This does not establish how the catalog's anonymous declaration is mapped or enforced. Configure the five-tool allowlist listed in this guide and require per-call approval **only if those controls and their behavior are available and verified**; otherwise stop and report the limitation, not auto-approve.
5. Test the saved agent in a Discovery shared session by selecting it or routing with `@AgentName`, as in the [Studio quickstart](https://learn.microsoft.com/en-us/azure/microsoft-discovery/quickstart-agents-studio). Microsoft also mentions a Foundry playground as an alternative interactive test in its [agent concepts](https://learn.microsoft.com/en-us/azure/microsoft-discovery/concept-discovery-agent#authoring-in-discovery-studio); [Foundry's SQL example](https://learn.microsoft.com/en-us/azure/data-api-builder/mcp/quickstart-azure-ai-foundry#step-7-view-tool-calls) shows reviewing tool calls, arguments and responses in Chat Playground. These are documented examples, not proof this agent appears or works in the user's environment. Review the actual tool call, endpoint, approval and error, not just the prose response. **New agent > Add existing agent** can copy an agent from another Discovery project; a project can contain multiple agents.

A separate direct [Foundry MCP integration](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol) requires an active Foundry project, appropriate role, model, reachable endpoint and approval handling; it does not establish that the Discovery catalog YAML is accepted as an SDK/REST request or that a separately created Foundry agent is the Studio agent. Catalog publication is another distinct path: a reviewed repository contribution surfaces catalog metadata in Studio, not proof of automatic deployment to the user's runtime.

The user manually created an agent in Studio and opened it in Foundry. An earlier access attempt was blocked by a network-access-unavailable message; a later user-observed Foundry Playground smoke test succeeded, including an approval and search response. The user also observed a no-match search. These manual tests do not establish deployment from this catalog YAML, full approval or allowlist enforcement, or independent verification of all returned data. Local edits here do not update the manually created agent; save a new version when applying changes.

The provider's available tools and schemas must be discovered again when connecting. In a local diagnostic run, `search_entities` resolved the disease, and `query_open_targets_graphql` returned focused schema introspection, association and evidence data. Do not assume every allowed tool is needed for every request.

## Data rights and provenance

The provider labels Platform data CC0 and describes permissions for listed data sources; its terms also note original-owner and third-party rights. Independently check original-source licensing and attribution before redistribution. Retain source IDs, query scope, data release when actually returned, and whether links were returned or constructed; a constructed link is not independently verified.
